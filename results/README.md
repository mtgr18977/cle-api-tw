# First pipeline run on the three case-study specs

Run on 2026-11-04 with the CC-News reference table (`reference/data/ccnews_en_min5.db`), thresholds t >= 2,
LL >= 3.84, min frequency 2, spaCy `en_core_web_sm`. About 21-28 s per API on 4 cores.

```bash
python specs/fetch.py
for n in stripe github kubernetes; do
  python -m apiterm analyze specs/data/$n.* --reference reference/data/ccnews_en_min5.db --out out/$n
done
```

`summary.json` per API is committed here; the CSVs are regenerated by the command above (`out/` is git-ignored).
**These are raw, unreviewed results: no precision has been measured yet (M5).**

## Finding 1: the three-tier triage collapses on these data

| | Stripe | GitHub | Kubernetes |
|---|---|---|---|
| Candidates with freq < 4 (cannot reach t >= 2, since t <= sqrt(c)) | 64.7% | 59.5% | 70.7% |
| Share of those in tier 2 | 84.8% | 81.6% | 87.5% |
| Tier-1 rate at freq 2-3 | 0% | 0% | 0% |
| Tier-1 rate at freq 4-9 | 56% | 57% | 57% |
| Tier-1 rate at freq >= 10 | 98% | 96% | 99% |
| Candidates with count 0 in the reference table | 78.6% | 83.1% | 85.7% |

* Tier 2 ("human review") is mostly low-frequency candidates that the t-score threshold can never accept.
* Tier 1 is in practice "frequency >= 4 and absent from the news sample": the specificity axis barely filters.
* The cause is the reference size (90k articles), not the pruning: on Stripe, the unpruned table lowers count-0 from
  78.6% to 68.4% but gives **identical** tiers (1,043 / 3,267 / 4 / 58).
* Thresholds are meant to be calibrated with the annotated sample (plan 4.7, M5); candidate options are a larger
  reference sample, a lower t threshold or PMI/Dice for low frequencies, and a higher LL threshold. Not changed yet.
* Tier 1 also contains generic documentation phrasing (*return list*, *contain detail*, *more information*,
  *see for information*) next to real terms (*payment method*, *pull request*, *access token*). Whether these count as
  CLE is an annotation-rule decision.

## Finding 2: operationId vs. description verb (RQ4)

| | Stripe | GitHub | Kubernetes |
|---|---|---|---|
| Operations compared | 0 (703 with no verb in operationId) | 1,259 | 1,172 |
| Same verb | – | 1,108 | 805 |
| Same semantic class | – | 5 | 0 |
| Different | – | 114 | 279 |
| Description has no verb | – | 32 | 88 |

* Stripe's operationIds start with the HTTP method (`PostAccountLinks`), so they carry no verb; GitHub's verb is in the segment
  after `/`; Kubernetes' is the first camelCase word. A first version of this analysis ignored that and reported a false
  mismatch for most Stripe and GitHub operations; `operation_id_words` now handles the three conventions (tested).
* Real divergences are informative. Kubernetes: 140 `patch` vs. *update* and 135 `list` vs. *watch*. GitHub: `get` vs. *list*,
  `update` vs. *set*, `create` vs. *start*/*run*.

## Verb variation

| | Stripe | GitHub | Kubernetes |
|---|---|---|---|
| Nouns with 2+ verbs (dependency) | 251 | 263 | 221 |
| Flagged as same-class verbs | 35 | 55 | 17 |

The flag needs human review. Grouping by noun mixes senses: GitHub's *request* combines *pull*, *merge* (pull request) with
*make* (API request), and prepositional labels (*remove from*) are compared with plain verbs (*delete*). Suggested
"preferred" verbs are therefore hints, not decisions.
